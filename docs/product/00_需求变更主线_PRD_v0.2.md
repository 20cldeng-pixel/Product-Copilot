## 1. 本轮范围

首版帮助非技术产品人员修改已有小型 Web 应用的业务规则，展示需求差异、影响边界及实际验收结果。复用 EasyMint 的 Pi、Mint、Builder/Evaluator 和既有界面能力；不新增 Research、独立 PRD Agent 或通用研发平台。

首个完整案例：将活动报名的“每位用户总共只能报名一次”改成“每位用户在同一活动只能报名一次，可以报名不同活动”。基线限定本地 React/TypeScript、模拟用户、单机顺序操作。活动样例与产品工作流分开，不能通过硬编码 CHG-001 的答案代替 Agent 实现。

首版只承诺支持明确范围内、具有已知行为基线的项目。任意历史仓库接管、真实鉴权、并发名额争抢、管理员例外、截止时间、取消报名及云端发布均不属于 CHG-001 的验收范围。

本文件及关联规格给出当前首版范围；此前 v0.1 中 AST/CodeGraph 深度映射、通用副作用幂等、自动续跑等内容保留为后续技术参考，不自动转成首版必做任务。角色能力限制、版本绑定、单项目串行写和原始证据保留仍为基础约束。

## 3. 用户流程

```text
用户描述变化
  → Mint 提取需求差异、读取当前基线
  → 生成 ChangeProposal：目标 + 影响 + 必须保持 + 验收计划
  → 处理阻塞性歧义
  → 用户一次“确认并执行”
  → 保存需求 v2，创建 Run
  → Builder 串行修改
  → 固定产物与测试版本
  → Runner 执行、Evaluator 解释证据
  → 展示通过 / 失败 / 未能判定，或单独记录人工决定
```

ProductWorkflowService 是贯穿全程的普通程序服务，协调状态、权限、版本和调度，不是新增 Agent。确认必须发生在用户看到影响和验收计划之后。

## 4. ChangeProposal 就绪条件

- 只要求会实质改变业务结果或使实现无法继续、且现有资料不能回答的问题得到解决。已有答案不重复问。
- 将问题分为 blocking / nonblocking；blocking 必须有答案，或用户明确采纳一项具体假设。不是所有问号都必须清零。
- Why 为可选补充；用户只想改规则时，不强迫其给出业务故事。模型推测的动机标为假设。
- 就绪还要求：基础需求版本未过期、Starter 基线已验证、影响分析有实际代码依据或明确未确定项、必选行为有可执行的验证计划。
- 用户确认绑定 Proposal 内容与基础版本。提案被修改或基础版本变化后，旧确认不能自动沿用。
- 本轮仅写规格；尚无 Starter 代码，因此 CHG-001 当前为 Draft，而非 Confirmed。

## 5. 最小界面

主操作围绕一次变更，历史检索围绕需求。Agent 运行细节在次级展开区。

```text
修改重复报名规则                         草案 / 待确认 / 执行中 / 结果

现在：每个用户只能报名一次
改为：每个用户在同一活动只能报名一次，可报名不同活动

影响：已核验关联 / 可能影响 / 尚不确定
保留：活动可浏览、开放状态、名额、人数变化、刷新及已有数据
验收：同场拒绝、跨场允许、多用户不互相限制、回归通过

[调整]                                  [确认并执行]

结果：逐条行为 + 观察结果 + 查看证据
次级入口：改动文件 / 运行日志 / Token 与耗时
```

原始文件路径对产品用户默认折叠，先显示“报名校验”“报名状态”“人数统计”等可理解对象。没有实际代码关联时显示“尚未建立关联”，不能把计划中的文件当作已核验结果。

结果页面区分“修改已执行”“自动验收通过”“界面待人工验证”“人工接受且保留例外”。一个大绿勾不能同时代表上述所有含义。

## 6. 四类核心数据对象

| 对象 | 最小字段及职责 |
|---|---|
| Requirement | id、version、behavior、sourceRefs、preserveRefs、verificationContract；保存已确认行为和验证计划 |
| ChangeProposal | id、baseVersion、targetDraft、why?、impact、questions、status、confirmation；未确认内容不能变成正式需求 |
| Run | id、requirementVersion、executionStatus、attempts、artifactRef、testSuiteRef、limits、usage、humanDecisions；保存执行和产物 |
| Evidence | id、runId、criterionId、artifactRef、testSuiteRef、method、rawOutcome、attachments；保存实际观察事实 |

影响项带 source 与 inspectedArtifactRef；历史映射属于旧版本关联，不能自动称为当前版本已确认影响。四类对象可以存在同一个由主进程单写的 JSON 中。PRD 和 task.json 是派生内容，不能反向覆盖权威确认。

Evidence 不接受“模型说 PASS”作为自动检查的原始依据。人工接受作为 Run 内独立记录，包含条目、理由和版本；不修改机器的原始失败或未判定结果。

## 7. 最小状态和服务动作

Proposal：draft → ready → confirmed；也可变为 rejected / superseded。就绪条件由服务验证，模型只能提出建议。

Run 执行状态：queued / running / completed / failed / interrupted / cancelled。Verification 是另外一组状态：not_run / pass / fail / inconclusive / stale。执行 completed 不等于 pass。

主要动作：读取上下文、提出变更、更新草案、用户确认并启动、提交执行结果、执行验证、记录人工决定、取消或重新运行。身份与权限由宿主绑定，不能依赖模型自填 actor 或 approved 字段。

第一版保留最小重复启动去重和 stateRevision 检查；相同命令重投先返回原提交结果，新命令才判断当前版本。一个项目一次只运行一个写任务。重启将未确认结束的运行标成中断，核对产物并确认旧写进程停止后才能重新启动，不做工具调用中途自动续跑。

代码、需求或对应测试变化后旧 Evidence 不计入当前结果。普通完全访问会话和外部编辑不属于强制隔离保证；产品模式通过受控工具、租约和产物快照限制影响，并检测当前文件与验收产物是否一致。

## 8. 首版实现与评测出口

1. M0：确认 Pi 工具能力可收紧，结构化输出可校验，产品结果可独立接收；保留普通任务的既有行为。
2. M1：实现并独立验收 Starter V1，记录代码版本和 fixture；同时建立 EVAL-01 评分器，证明它能区分正确与错误变更。
3. M2：将 CHG-001、需求合同和界面接起来；Builder 使用真实模型完成修改，Runner 产生真实证据。
4. M3：跑完整 V1→V2 案例，包括保留旧数据、失败收尾和人工决定。再用不同输入组合检查是否写死演示。
5. M4：比较原 EasyMint 与改进版。固定业务信息、模型、资源上限和用户回答规则，保留失败与人工成本；新增独立任务才承担未见评测。

本轮完成的是上述规格，未完成 Starter、Runner、评分器、集成或效果测量。当前不得写“已提升成功率”“已经可靠恢复”“已支持自动验收”等成果结论。

## 9. 接下来只需确认的实现选择

- 持久化采用何种具体实现，在 M1 前确定并写入 Starter manifest；对外行为以 BR 为准。
- 刷新后页面状态的固定浏览器检查能否稳定运行，在 M0/M1 验证；不可用时明确采用人工检查，不默认自动覆盖。
- 准确的模型 ID、工具版本与运行上限，在比较试验前冻结。预算内各阶段消耗均须记录。

这些选择由技术探针提供依据，不再引入新的高层模块。

# 首版实现任务与验收

日期：2026-09-20。依据：[完整产品主线 PRD v0.3](./00_完整产品主线_PRD_v0.3.md)。以下均为待实现任务，不是已完成记录。

## 1. 实现顺序

```text
T0 固定上游、跑通应用与能力探针
  → T1 产品状态和执行权限
  → T2 需求分析、调研、优先级与 PRD
  → T3 原型及开发确认
  → T4 创建开发与证据验收
  → T5 任意阶段变更和 V1→V2
  → T6 交付质量与业务观察复盘
  → T7 贯通演示和独立对照评测
```

测试数据、业务指标定义和评分器可与界面开发并行准备；同一项目代码写任务仍串行。T2/T3 是正式交付功能，不能因为变更演示先跑通就从首版中删除。

## 2. 任务与退出条件

| ID | 实现范围 | 可检查的退出条件 |
|---|---|---|
| T0 | 在正式开发目录固定上游版本；运行原应用；检查模型、搜索、原型、结构化结果、角色工具和测试入口 | 有环境记录与实际运行结果；不可用能力明确标 blocked，不用 README 代替验证 |
| T1 | ProductPlan 与四类对象、主进程服务、IPC、阶段状态、批准、单写、预算与中断状态 | 模型不能自行批准；未批准不能开始正式开发；重复点击只创建一次 Run；旧版本拒绝推进 |
| T2 | 需求摘要、问题列表、来源卡、竞品对比、本次范围/优先级和 PRD 草案 | 一次普通用户输入能形成可修改产物；来源不足有出口；界面编辑与导出文档一致 |
| T3 | 复用原型生成与预览；关联需求；范围/原型两次关键确认；技术预审 | 原型引用当前需求；修改已批准行为能更新批准状态；未解决可行性阻塞不能开始开发 |
| T4 | 开发基线、Builder 执行、固定产物、Runner 与 Evidence、结果页 | 真实模型生成可运行 V1；各必验条目有真实记录；执行完成不直接显示通过 |
| T5 | 草案直接编辑、已确认内容的变更提案、影响/保留项、暂停/版本失效、回归 | 早期变更返回正确阶段；已交付 V1 完成 CHG-001，旧报名保留，旧结果不能把 V2 变绿 |
| T6 | Run 汇总、交互计数、样例事件采集和本地读取、确定性统计、复盘建议 | 结果可复算；合成/试用数据分开；空数据不显示增长；建议不会未经确认修改产品 |
| T7 | 创建、变更、贯通三类试验；固定输入/预算；原版与改进版对照 | 保存完整配置和成功/失败记录；区分已调试校准案例和未见案例；成果表述与证据一致 |

## 3. 代码落点建议

以下是待新增的建议路径，不表示文件已经存在：

| 建议位置 | 职责 |
|---|---|
| `app/shared/product-workflow.ts` | 共享业务类型、校验规则、IPC 数据契约 |
| `app/main/services/product-workflow-service.ts` | 状态迁移、确认、执行调度、版本与预算约束 |
| `app/main/services/product-workflow-store.ts` | 项目级状态读写、原子保存、revision 和命令去重 |
| `app/main/services/tools/product-workflow-tool.ts` | 模型可调用的草案/来源/提案工具；无代用户批准能力 |
| `app/main/services/product-verification-runner.ts` | 固定产物执行检查、保存结果，不用模型输出冒充退出码 |
| `app/main/services/product-review-service.ts` | 汇总交付记录、读取样例事件、计算复盘指标 |
| `app/renderer/src/components/product/` | 阶段产物、变更卡、验收结果与复盘视图 |

复用现有 agent-service、task executor、原型预览和项目创建入口；具体拆分在 T0 后根据现有 IPC 和存储规范调整。无需新增向量库、图数据库、消息队列或整套工作流框架。

产品状态属于工作流宿主，放在被构建样例的可写目录之外。Builder 工作区包含应用代码和获准公开的需求视图，不包含可任意覆盖的批准与证据真源。评分器材料另置于运行代理的可读范围之外；名为 author-only 的普通目录本身没有隔离效果。

若某次应用内会话被授予完全访问，其隔离保证须明确降低；不能用路径约定或提示词宣称已强制阻止越权。T0 需证明所选产品模式可以实际执行约定权限，否则该能力标阻塞。

## 4. 最小服务契约

| 动作 | 发起者 | 服务必须检查 |
|---|---|---|
| 保存计划/需求草案 | 用户编辑或 Mint | schema、版本、未覆盖正式批准；变更内容记录修订 |
| 登记研究来源 | Mint 的受控工具 | 来源引用、读取状态、事实与推断字段；不让外部页面内容充当指令 |
| 确认首版范围 | 真实用户操作 | 当前计划版本、阻塞问题、明确范围与验收计划 |
| 提交原型 | Mint/设计执行结果 | 产物存在、当前需求关联；提交不是用户批准 |
| 确认并开发 | 真实用户操作 | 当前需求/原型/测试计划/预算、可行性、写任务占用；幂等启动 |
| 提出变更 | Mint 或用户编辑 | 基础批准版本、当前产物、目标差异、保留项、影响依据 |
| 确认变更 | 真实用户操作 | 基础版本未过期、影响已刷新、必要的新原型可见、执行范围与预算 |
| 提交执行产物 | Builder 执行回调 | runId、实际工作区状态、写进程已停止；不接受模型自报通过 |
| 提交验证证据 | 受控 Runner | 需求/产物/测试匹配、真实执行、必验条目完整性 |
| 人工验证或接受例外 | 真实用户操作 | 指定条目、理由、产物与合同版本；不覆盖原始结果 |
| 生成复盘 | 服务统计与 Mint 解释 | 来源和统计口径、缺失字段、版本及数据集边界 |

来源材料与行为验证证据分开：ProductPlan 的 researchSources 支持调研事实；Evidence 支持某项验收的实际观察。某竞品网页提到持久化，不能成为本项目已实现持久化的证据。

研究阶段可调用受控联网工具并保存调研结果，但不能修改应用代码；Builder 只写受限应用工作区；Runner 按冻结测试配置执行。角色权限由宿主装配，不能只靠 Agent 名称或提示词约束。

确认动作先检查已提交命令的去重记录；新命令在串行临界区判断版本并保存状态。两个不同按钮事件同时到达时，最多一个获得当前批准/写任务资格。

## 5. 必须提前统一的旧逻辑

1. **优先级**：统一为 P0/P1/P2，修订当前提示词与功能共创指引中的不同编号，避免同名优先级含义相反。
2. **PRD 生成时机**：原型前写草案，原型后确认开发基线；均来自同一需求数据。
3. **确认依据**：产品模式使用真实事件和内容版本；旧“确认开发”提示词不能直接批准状态。
4. **完成状态**：产品模式的 task done 是执行视图，不能替代需求验收通过；业务结果由 Evidence 汇总。
5. **跳过流程**：原普通模式保留既有行为；产品模式下“快速开始”可以减少追问或声明跳过调研，但不能伪造确认和验收。已选择的快速探索策略也作为用户授权记录。
6. **结构化结果**：必须由代码校验字段与状态；不采用“LLM 输出 JSON 就算有效”的做法。

## 6. 测试与演示场景

这些检查围绕错误状态、数据副作用和用户承诺，避免仅复刻实现细节。

| 场景 | 主要检查 |
|---|---|
| 正常创建 | Idea→有来源调研→确认范围→原型→确认开发→V1→证据→复盘能完整通过 |
| 无联网能力 | 明确显示调研不可用；用户补充材料或按假设继续；不会出现伪造来源 |
| 原型阶段改需求 | 批准的范围变化得到新确认，旧原型批准失效，只返回相关阶段 |
| 开发中收到新想法 | 新草案可保存，旧写任务不与新任务并发；确认使用最新产物 |
| 提案内容或测试标准变化 | 旧确认不会默默沿用，必要时重新确认 |
| 子任务正常结束但业务失败 | 执行可以 completed，验收必须 fail 或 inconclusive |
| 重复启动及进程中断 | 重复点击不重复执行；重启显示中断并核对旧进程，不能直接续写 |
| 报名规则升级 | 使用既有 VC-01～VC-08 与 EVAL-01 校准，保留 V1 数据 |
| 定位器/环境故障 | 先区分验证故障与业务失败；没有证据不判 pass |
| 人工接受失败版本 | 保留失败事实，另外记录用户决定；不提高自动通过率 |
| 业务数据复盘 | 去重、窗口、版本和来源筛选正确；零分母为 N/A；合成数据有标记 |
| 预算与修复上限 | 达上限后保存产物和原因，不能无限修复或把停止包装为成功 |

T0 运行原项目既有检查建立基线；之后根据触及的代码运行对应测试，必要时执行类型、构建和原有回归检查。没有代码变更的设计文档不声称已通过应用测试。

## 7. 试验材料的组织方式

- **创建开发案例**：公开 Idea、约束、用户回答脚本与验收语义；保存首次提案质量及最终行为。以模型生成的应用为实际产物。
- **固定变更校准**：使用 [Starter 基线](./01_Starter_行为基线.md) 和 [EVAL-01](../../evaluation/author-only/EVAL-01_独立评测案例.md)，两组起点保持一致。
- **贯通案例**：使用本次创建的 V1 继续变更，不把它的结果与固定基线试验混为同一分母。
- **未见案例**：在调试后另外制定，评分代码和参考实现隔离；每条判据可回溯到公开业务要求。

同时保留两种结果：产品对用户的声明、独立检验的实际结果。创建/变更/贯通各自统计成功、失败、未判定及人工成本；只测活动报名时，不能宣称适用于所有产品类型。

# Activity Registration Starter：V1 行为基线

版本：BR-BASELINE v1。状态：待实现、待验收的公开规格，不代表已有运行项目。

## 1. 使用范围与术语

本地 React/TypeScript 演示应用，固定模拟用户身份，可浏览多场活动并报名。身份切换只是测试与演示机制，不代表真实登录或权限系统。操作顺序执行，不测试多设备同步或并发抢名额。

用户、活动具有稳定且不同的 ID。一个报名记录必须能确定对应用户和活动；不强制具体存储结构、函数名称或文件名称。`registeredCount(A)` 表示活动 A 的实际有效报名数量，可以由记录计算，也可以维护为字段，但必须与记录一致。

活动有开放状态和容量。名额按活动分别计算。首版无取消报名，因此不存在取消记录是否有效的额外规则。

## 2. 公开行为规则

| ID | V1 行为 | 可观察结果 | CHG-001 后 |
|---|---|---|---|
| BR-01 | 用户可以查看活动列表和活动信息 | 能区分活动及其开放/满额状态 | 保持 |
| BR-02 | 用户可以向开放且满足其余规则的活动申请报名；关闭活动拒绝报名 | 成功或明确拒绝，不静默无响应 | 保持 |
| BR-03@v1 | 同一用户在整个系统中最多成功报名一场活动 | 报名 A1 后，再报 A1 或 A2 均被拒绝；其他用户独立判断 | 被 BR-03@v2 替代 |
| BR-04 | 活动人数达到 capacity 后拒绝新的报名 | 活动计数不超过其容量；不影响另一活动的名额 | 保持 |
| BR-05 | 一次成功报名只增加一条该用户、该活动的有效关系，该活动人数加一 | 其他活动人数不变；不会一次点击重复加数 | 保持 |
| BR-06 | 任何失败报名都不产生报名记录、不改变各活动人数 | 重复、满额、关闭均满足这一约束 | 保持 |
| BR-07 | 页面刷新后，原有报名、人数和当前用户的活动报名状态保持；本次规则升级也必须保留既有有效报名数据 | U1 曾报名 A1，刷新或升级后仍可识别；不能靠清空数据实现改动 | 保持 |

BR-07 的“规则升级保留已有数据”在这里公开约定，独立评测不能临时添加此条件。它不要求未承诺的跨浏览器、跨设备或账户同步。

页面应区分“已报名本活动”与“因其他规则暂不可报名”。V1 的全局报名限制不应把 U1 错误显示为已报名所有活动。

## 3. 固定测试数据

| 类型 | ID | 属性 |
|---|---|---|
| 用户 | U1、U2、U3 | 三个不同的模拟用户 |
| 活动 | A1 | 开放，capacity=2 |
| 活动 | A2 | 开放，capacity=2 |
| 活动 | A3 | 关闭，capacity=2 |

使用三组独立 fixture；每组开始重置，组内步骤之间不清空状态：

切换模拟用户与重置 fixture 是不同操作，身份切换不得清空报名数据。刷新检查前后均选择指定用户；若刷新使身份选择器复位，可重新选择该用户再观察，不额外要求模拟身份本身持久化。

- **F0 空数据**：所有活动人数为 0，无报名记录。
- **F1 既有数据**：先在通过基线验收的 V1 中执行 U1→A1 成功，得到真实持久化状态；A1 人数为 1，A2/A3 为 0。
- **F2 关闭活动**：全空状态，用来单独验证 A3 拒绝报名。

F1 不能直接由 V2 的测试夹具伪造为“迁移已成功”。允许复制 V1 产生的 fixture 快照，但必须记录生成它的基线版本。

## 4. V1 自身的验收

| ID | 前置与操作 | V1 预期 |
|---|---|---|
| BVT-01 | F0，查看活动 | A1/A2/A3 可区分，开放状态符合 fixture |
| BVT-02 | F0，U1→A1 | 成功；仅 A1 计数变为 1 |
| BVT-03 | 接 BVT-02，U1→A1 | 拒绝；计数与记录不变 |
| BVT-04 | 接 BVT-03，U1→A2 | V1 全局限制拒绝；A2 仍为 0 |
| BVT-05 | 接 BVT-04，U2→A1；再 U3→A1 | U2 成功且 A1=2；U3 被拒绝且计数仍为 2 |
| BVT-06 | 接 BVT-05，切回 U1 后保留同一存储并刷新 | U1 对 A1 已报名；对 A2 未报名，人数及记录不丢失 |
| BVT-07 | F2，U1→A3 | 拒绝；全部计数及记录不变 |

BVT-04 的旧期望在 CHG-001 中被明确替代，不能作为“不允许变化的回归测试”继续强制失败。其他行为按同一语义回归；测试名称或私有函数重构不能单独判成业务失败。

## 5. 基线正式启用条件

- Starter 代码已实现，以上检查得到真实结果。
- 记录源码版本/内容摘要、依赖锁文件、环境、持久化方案及 fixture 生成方式。
- 区分自动检查与人工检查；尚未运行的项保留 not_run，不能预填通过。
- 两个被比较系统使用同一基线副本和同一公开 BR 文档；每次运行从干净副本及指定存储状态开始。

本规格不预先认定 V1→V2 必然涉及数据库结构变化。如果已有数据已包含 userId/activityId，可能只需修改校验、查询和界面状态；实际影响必须查看实现后判断。

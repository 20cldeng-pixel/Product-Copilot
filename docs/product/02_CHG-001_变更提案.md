# CHG-001：重复报名规则的作用域变更

提案版本：1。状态：**Draft**。原因：业务含义已明确，但 Starter 尚未实现验收，文件关联和验证器能力尚未核查。未记录用户确认、运行 ID 或通过结果。

公开依据：[Starter BR-BASELINE v1](./01_Starter_行为基线.md)。目标合同：[REQ-REG-001 v2](./03_REQ-REG-001_v2_验收合同.md)。

## 1. 这次改什么

用户请求：“把规则改成每个用户每场活动只能报名一次。”

- **原规则 BR-03@v1**：一个用户在整个系统中最多成功报名一场活动。
- **目标规则 BR-03@v2**：同一用户不能重复报名同一活动；可以报名不同活动。不同用户报名同一活动互不构成重复，仍受活动容量限制。
- **Why**：可选。当前请求已足够定义变化，不要求用户额外填写动机。未提供的业务收益不写成事实。

这次不引入取消报名、截止时间、管理员特权、真实鉴权或并发保证。

## 2. 哪些行为必须保持

保持 BR-01、BR-02、BR-04、BR-05、BR-06、BR-07。既要保留活动浏览和开放状态，也要保留容量、计数、失败无副作用、刷新及既有数据。

BR-03@v1 被明确替代，不保留“跨活动也拒绝”的旧断言。其余回归测试不能因实现不通过而自动删除、跳过或放宽。

## 3. 影响预览

尚无 Starter 代码，以下均为**预期分析对象**，不是已核验文件或精确影响结论：

| 对象 | 当前判断 | 后续核查内容 |
|---|---|---|
| 报名重复性校验 | 预计直接相关 | 是否由 userId 全局判断变为 userId+activityId 判断 |
| 报名记录读取与持久化 | 待核查 | 是否已保存活动归属；是否需要修改查询或结构 |
| 当前用户的活动报名状态 | 预计相关 | 报了 A1 是否仍错误阻止或显示已报名 A2 |
| 报名按钮和结果反馈 | 可能相关 | 按钮可用性、拒绝原因与新的业务规则是否一致 |
| 容量与计数 | 必须回归 | 去重变化是否引入重复加数、跨活动计数污染 |
| 测试 | 预计直接相关 | 替换旧全局去重期望，补跨活动成功、多用户和旧数据验证 |

进入实际流程后，将每项更新为“已核验关联 / 可能影响 / 尚不确定”，附对应产物版本和依据。Builder 申报清单需要和实际变更对照；文件曾有关联不意味着当前一定受影响。

影响预览不减少本案例核心回归范围。没有发现某项影响不等于证明其不存在。

## 4. 未决问题与假设

- **阻塞性业务歧义：当前没有。** “每个用户每场活动一次”已经表达允许跨场活动；再次询问该点属于确认性提问，不算发现了新的关键歧义。
- 沿用 BR 对用户身份、开放状态、名额及保存行为的定义，不重复向用户询问。
- **执行准备阻塞：存在。** 需要通过 Starter 基线、建立真实影响依据、确定 VC-05 展示部分及 VC-08 页面验证的可用方法。
- 不把“暂无业务问题”解释为“已经可以执行”。

## 5. 用户确认的内容

确认卡同时展示：

1. 同场不能重复、跨场可以报名、不同用户相互独立。
2. 保留全部未变更 BR，已有报名数据不能丢失。
3. 影响分析的确定项和不确定项。
4. VC-01～VC-08 的验证计划及需要人工检查的项目。

在准备条件满足、基础版本仍有效后，按钮显示“确认并执行”。点击后才记录 proposalId、提案版本、基础需求版本、实际确认时间及批准范围，生成正式 Requirement v2 和 Run。

业务规则或验收计划实质变化时重新确认；只更新运行日志不要求重复确认。用户拒绝或取消不构成授权。

## 6. 结果与异常交互

- Builder 完成：显示“修改完成，正在验证”，不立即显示通过。
- 证据符合当前版本：逐条展示通过，并提供日志/截图入口。
- 明确业务失败：展示对应标准、实际行为和有限修复选项。
- 环境错误或证据不足：显示“未能判定”，不把它包装成产品功能失败。
- 用户可按条目手动验证，或“接受当前版本并保留例外”；两者另记决定，不改变自动测试事实。
- 新变更确认后，旧结果归档；旧 Run 的迟到通知不能把新版本变绿。

# REQ-REG-001 v2：按用户与活动去重

状态：**供确认的目标合同**；CHG-001 在真实应用中被确认后才成为已确认需求。当前全部检查为计划项，未产生 Evidence。

来源：[CHG-001](./02_CHG-001_变更提案.md)。公开基线与 fixture：[BR-BASELINE v1](./01_Starter_行为基线.md)。

## 1. 行为

- 一个用户在同一活动最多有一条有效报名。
- 同一用户可以报名不同活动。
- 不同用户可以报名同一活动，各自独立判断重复；仍受该活动开放状态与容量限制。
- 保留 BR-01、BR-02、BR-04、BR-05、BR-06、BR-07，特别是本次升级前的有效报名及人数。

规则替代关系：BR-03@v1 → BR-03@v2。系统不能同时要求跨活动成功和旧版本的跨活动拒绝。

## 2. 验证计划

每条检查都要记录前置条件、实际观察和所测版本。“核心回归通过”展开为下列具体条目，不能用一次笼统 PASS 替代。

执行分组：F0 连续执行 VC-01～VC-04、VC-06，并在指定节点执行 VC-08 的页面观察；之后独立重置 F2 执行 VC-05，独立准备 F1 执行 VC-07。表格顺序不是跨 fixture 连续操作顺序，F0 组内不清空数据。

身份切换和刷新沿用公开 fixture 约定：刷新后可重新选择 U1，不能清空报名状态；不把模拟身份选择器是否持久化作为附加验收条件。

| ID | 条件与操作 | 应当观察到 | 计划方法 |
|---|---|---|---|
| VC-01 | F0，U1 首次报名 A1 | 成功；只有 A1 人数由 0 变 1，记录唯一 | 业务/集成检查 |
| VC-02 | 接 VC-01，U1 再报 A1 | 拒绝；记录和各活动计数不变 | 业务/集成检查 |
| VC-03 | 接 VC-02，U1 报名 A2 | 成功；A1=1、A2=1，两条活动关系独立 | 业务/集成检查 |
| VC-04 | 接 VC-03，U2 报名 A1；再 U3 报 A1 | U2 成功并使 A1=2；U3 满额被拒，计数仍为 2；A2 不变 | 业务/集成检查 |
| VC-05 | F2，U1 报名关闭的 A3 | 拒绝；没有新增记录或人数变化；活动仍可查看 | 业务检查及活动展示检查 |

这些是业务验收语义，不强制任何私有函数、DOM 类名或内部存储键。具体 Runner 适配器在 Starter 实现时确定；定位或适配错误先分类为验证问题，不能直接归因为业务缺陷。

## 3. 测试自身的校准

关键校准至少包含：

- 正确按 userId+activityId 判断的实现应通过去重语义。
- 未修改的 V1 全局限制应在 VC-03 失败。
- 完全取消重复校验的实现应在 VC-02 失败。
- 升级时清空旧数据的实现应在 VC-07 失败。

校准样例用于验证测试是否能发现对应缺陷，不代替完整业务验收。参考正确实现只能提供给测试作者，不能作为被评测 Builder 的解答。

## 4. 计划覆盖与本轮结果分离

合同只声明计划。不得在生成合同后直接填写 `Unverified: none`。

确认时需要选定 VC-05 的展示部分及 VC-08 的方法；两者可以复用同一套固定页面检查：

- 浏览器检查可稳定执行：纳入自动必验项。
- 仅能人工检查：确认卡明确显示“页面状态需人工验证”。机器可显示“自动部分通过”，整体不得宣称全部自动验收通过。

自动结果为 pass / fail / inconclusive，另有 not_run 和 stale 生命周期标记。零用例、必选项跳过、退出失败、产物版本不匹配、没有真实执行记录都不能算有效通过。重试中出现矛盾结果保留不稳定标记，不以最后一次绿色覆盖历史。

人工验证、人工接受例外单独记录条目、理由、需求版本、产物快照及所依据的测试版本。无法自动验证是方法限制，不是人工已经验证。

## 5. 证据最低要求

每条 Evidence 包含 runId、criterionId、requirementVersion、artifactRef、testSuiteRef、method、观察结果、时间和附件引用。源码快照包含未提交内容；测试方法和环境一并记录。

Runner 保存原始执行事实，Evaluator 解释结果及原因。Builder 不得通过删除检查、修改基准或伪造报告获得通过。需要修订测试时保留版本和理由，重新验证；改变业务成功标准则回到 ChangeProposal。

本合同未覆盖真实鉴权、并发报名、跨设备持久化、截止时间或管理员例外。结果页不得将本案例通过扩大表述为完整生产系统已验证。

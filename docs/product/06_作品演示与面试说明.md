# Product Copilot 作品演示与面试说明

## 一句话

一个把自然语言需求、原型确认、Agent 开发和验收证据连接起来的本地产品工作台，重点研究交付后的需求变更。

## 90 秒介绍

我选择的场景是非技术用户用自然语言修改已有应用。难点不只是生成代码，而是需求变化之后，哪些原有规则和数据必须保留，以及系统凭什么说已经完成。

我用活动报名做了一个完整案例：从每人只能报名一场，改为每人每场只能报名一次。它同时涉及需求歧义、旧数据迁移、界面资格和回归检查。

产品里，Agent 可以整理需求和变更提案，但范围与原型由用户确认。开发结束之后，系统运行真实测试，把结果关联到验收条件；需求、原型或代码变化时，旧批准和旧证据会失效。人工核验也独立留痕。

目前示例完成了 36 项测试，26 条 P0 条件的关联检查通过，并做了独立业务探针和浏览器操作验证。公开固定案例两组各 3 次仍都是 3/3。随后我做了一个运行前未展示给 Agent 的 DeskFlow 案例：两组对用户原始需求都 3/3，只有合同额外写明的 schema 治理要求出现 A 0/3、B 3/3。因为数据结构没变，这不能包装成成功率提升，反而说明实验判据也要接受产品审查。B 更慢、调用更多、cost 估算更高；当前能证明的是需求和治理条款更可追溯，不能证明净收益。

## 三分钟演示

| 时间 | 页面或操作 | 观众应看到什么 |
|---|---|---|
| 0:00–0:30 | 产品计划、已确认范围、当前 PRD | 需求和验收条件是可编辑产物，不仅在聊天里 |
| 0:30–1:00 | CHG-001 提案差异及保留项 | 同场一次、允许跨场；容量、关闭和旧数据需要保留 |
| 1:00–1:30 | 已保存的失效/异常运行记录 | 开发结束、未判定、证据失效和通过有不同含义 |
| 1:30–2:15 | Gather 成员视图 | U1 报开放活动；重复拒绝；另一场开放有余位则可报名 |
| 2:15–2:40 | 刷新、管理员名单 | 人数和报名记录保留，满额与关闭仍限制新增 |
| 2:40–3:00 | 复盘与评测记录 | 本地模拟数据、预实验与正式结果明确区分 |

演示前检查活动是否有余位；默认 A2 已满，可由管理员新建容量为 2 的活动。不要清空用户的既有浏览器数据，使用新的演示 origin。需要展示旧数据迁移时使用冻结 F1 与对应验证记录，不把已迁移的页面假装首次升级。

## 常见追问的证据入口

| 问题 | 回答要点 | 证据 |
|---|---|---|
| 为什么不直接让模型说通过？ | 模型正常结束不代表业务正确，测试结果也需要覆盖关系 | `product-verification-service.ts` 及对应测试 |
| 如何避免旧结果沿用？ | 对需求、原型和产物保存摘要，读取时判断当前有效性 | `product-workflow-service.ts`、`evaluation/reliability/20260921.md` |
| AI 写测试也会写错怎么办？ | 显式检查关联、保留未判定、人工核验、独立评分和缺陷校准 | `evaluation/gather/calibration-20260920.json` |
| 比原版好多少？ | 用户原始需求仍无提升证据；未见案例中扩展合同 0/3→3/3 只证明额外 schema 条款遵从，且 B 更慢、调用更多 | `evaluation/formal-ab-20260921/`、`evaluation/holdout-sla-20260921/` |
| 复盘数字是真实业务吗？ | 是固定身份的本地试用或合成数据，不能称线上转化提升 | `product-review.ts` 及对应测试 |
| 最大的取舍是什么？ | 确认与接入增加成本，必须通过复杂变更及恢复场景验证收益 | 预实验交互记录 |

## 当前不能使用的表述

“成功率提升 X%”“节省 X% 成本”“已验证生产安全”“所有 UI 自动验收”“所有取消/异常都已实测”。现有公开案例与未见案例的原始需求核心差异都是 0 个百分点；扩展合同的 0/3→3/3 受额外 schema 条款混杂，不能换一种方式包装成成功率提升。没有完整对应证据时，不填这些指标。

本文件是演示脚本与面试准备材料，尚不代表已经录制完成演示视频。

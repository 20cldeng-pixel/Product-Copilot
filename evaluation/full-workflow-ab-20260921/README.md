# EVAL-03 完整工作流重复 A/B

日期：2026-09-21。分类：正式、脚本化的完整工作流重复实验。案例为从空项目创建 ShiftLoop V1，再将“每人全局最多认领一个班次”改为“可认领多个不重叠班次”，数据形态因此必须支持一名成员对应多条认领记录。

## 方法

- A/B 各运行 3 次，顺序为 A1、B1、B2、A2、A3、B3；六份项目从相同的 4 文件空白 Starter 开始，初始 Git tree 均为 `dcd8277d3a45797d6d0bbbc38586041013ebc96e`。
- 两组使用相同的 OpenAI Codex `gpt-5.6-sol`、medium 思考、read/bash/edit/write 工具，以及 5 条脚本化用户消息。每一轮消息的墙钟上限为 300 秒，没有 Token 或金额硬上限。
- A 只获得共同执行约束。B 额外获得 Product Copilot 协议：维护产品材料、范围和原型确认后开发、变更前记录影响与迁移、需求锚点、确定性测试及复盘边界。
- 主结果要求 5 轮全部正常结束，且 V1、V2 独立探针均通过。任何一轮超时都保留为失败样本，不重跑、不延长上限，也不把停止时的部分代码改判为完整成功。
- 评分器在运行前以正确参考实现校准：V1 为 8/8，V2 为 12/12；空白 Starter 因缺少必需适配器被拒绝。评分器和参考实现均不在被评测项目内，六轮未发现读取父目录或评测器的工具调用。

| B Product Copilot 协议 | 0/3 | 3/3 | 7 | 4 | 438.904 秒 | 33.333 | 1.068850 |

| 运行 | 终止位置 | 墙钟 | 停止时 V1 探针 | 停止时 V2 探针 |
|---|---|---:|---:|---:|

A 三轮在收到首条“从需求分析开始”后都直接进入实现，并在首轮超时；停止时业务规则检查已通过，但缺 PRD 和原型材料。B1 完成前两轮产品材料，在正式 V1 开发轮超时。B2、B3 虽然尚未收到第 3 条原型确认消息，停止时已出现业务实现，违反了 B 协议的开发闸门；两份实现还把新建班次固定为关闭，未遵守评分适配器传入的 `open` 状态。

停止时探针是补充诊断，不改变主结果。六轮没有一份完整通过 V1，且都未进入 V2 变更、迁移、验收和复盘，因此本实验没有可比较的最终验收成功样本。

## 可支持的结论

本案例只能说明：Product Copilot 协议让 B 组在超时前平均到达更多工作流阶段，B1 也确实延后到用户确认原型后才开发；协议本身尚未稳定约束所有运行，B2、B3 仍提前实现。两组端到端完成率均为 0/3，不能支持“提高交付成功率”“减少返工”或“缩短耗时”。B 总耗时更高主要因为运行了更多轮次，不能直接解释为同阶段效率下降。

用户回复是固定脚本，因此真实人工耗时未知。运行中没有操作员纠错，也没有把独立评分反馈给 Agent；人工返工次数无法从日志可靠计算。SDK cost 是客户端估算，未与账单核对。执行环境没有 `npm` 命令，部分运行改用 `node --test` 与构建脚本；这一环境限制可能影响时长，不能从本实验外推生产表现。

配置见 [`manifest.json`](./manifest.json)，聚合及逐轮指标见 [`results.json`](./results.json)，共同输入见 [`messages.json`](./messages.json)，评分器与校准见 [`scorer/`](./scorer/)，逐轮冻结摘要与探针见 `runs/*/summary.json`。原始 JSONL 和完整源码快照保留在本地忽略目录，公开证据不包含账户、凭据或私人配置。

## 实验后的产品改进

复查确认，本实验的 B 组是相同 CLI 上附加 Product Copilot 提示词协议，并没有调用桌面产品中已有的主进程阶段状态机。因此 B2/B3 的提前实现证明提示词约束不稳定，不代表正式产品闸门失效。实验结束后，正式 Builder 在既有范围/原型批准检查之上增加执行批次：每轮最多 2 项 P0，运行记录冻结对应需求 ID，失败或取消重试原批次，全部需求批次正常结束后再进入一次集成补缺。后续已用真实桌面入口完成一个 3 P0 的 2/1 批次及集成 smoke，并修复集成完成后可重复启动的问题，见 [独立记录](../batched-build-smoke-20260921/README.md)。该结果不回写本实验，也不是新的重复 A/B。

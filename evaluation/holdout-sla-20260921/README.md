# EVAL-02 独立未见案例：DeskFlow SLA 变更

日期：2026-09-21。分类：作者自建、运行前未提供给被评测会话的固定变更 holdout。案例和隐藏评分器先在本地冻结并校准，再按 A1、B1、B2、A2、A3、B3 顺序运行；发布后该案例不再能作为未见任务复用。

## 任务与方法

共同原始输入是：“把工单 SLA 改成紧急工单 4 小时、普通工单 24 小时；已有工单的截止时间保持不变。”六轮均从 DeskFlow V1 提交 `b46f25b3f35fbc75db6f73931f6046291550a0f6` 建立，21 个受控源文件摘要一致。

- A 组只获得共同执行约束和原始输入。
- B 组额外获得冻结的 Product Copilot 合同，其中列明绝对小时、旧工单逐字段保留、纯函数失败语义、schema 升版、损坏快照修复、影响文件和排除项。
- 两组使用 OpenAI Codex `gpt-5.6-sol`、medium 思考、read/bash/edit/write、600 秒墙钟和 80 次工具调用上限。没有 Token 或金额硬上限；B 输入更长，不能称为严格等 Token 或等费用。
- 六轮结束并冻结源码后，统一运行同一个隐藏探针、项目测试和生产构建。评分器在运行前已证明：未改 V1 为 5/9，已知正确参考实现为 9/9。

## 结论与实验缺陷

冻结主终点的确得到 A 0/3、B 3/3，但不能据此宣称 Product Copilot 把同一任务的开发成功率提高了 100 个百分点。原因是数据结构没有变化，原始输入并不必然要求 schema 升版；A 的实现满足了原始需求核心语义。这个实验更准确地证明：明确写入合同的治理要求能稳定提高该要求的遵从率，同时增加了可观察的执行时间、工具调用和 cost 估算。

“核心 7 项”是在揭盲后用于解释合同是否过度规定的子集，因此属于事后分析，不能替换冻结主终点。案例由项目作者创建、每组只有 3 次、只覆盖固定代码变更，也不足以推断泛化或统计显著性。下一轮应选择一个数据形态必须变化的未见任务，或者在运行前由独立评审确认每条隐藏判据都由共同用户目标必然导出。

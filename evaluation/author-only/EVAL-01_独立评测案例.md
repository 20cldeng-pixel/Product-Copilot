# EVAL-01：报名去重作用域变更的独立评测

版本：1。用途：**公开开发校准案例**，不是 hold-out。状态：Starter、探针校准、单次页面配对预实验及固定变更执行的 A/B 各 3 次重复对照已完成；结果见 [`formal-ab-20260921`](../formal-ab-20260921/README.md)。该重复实验使用 Gather 专用独立 VC 探针，不等同未见案例或通用页面黑盒评分。

## 1. 独立性的边界

公开业务来源：[Starter 行为基线](../../docs/product/01_Starter_行为基线.md)、[CHG-001](../../docs/product/02_CHG-001_变更提案.md)、[目标合同](../../docs/product/03_REQ-REG-001_v2_验收合同.md)。本文件编写独立的检验顺序与判定，不允许添加只有评分者知道的业务要求。

真实评测时，具体评分代码、参考实现和测试数据置于被评测 Agent 的文件/工具权限之外，且不注入产品 Prompt。author-only 目录只是组织标记。Runner 的产品测试和这里的独立评分器不共用模型生成的判定结果；可以共用公开协议和受控基础设施，但评分断言由作者独立核查。

冻结被评测产物后才执行评分。评分详情不回传给同一次运行继续修复。开发校准允许查看并修订方案，但必须记录为新的实验配置；不能把调过的案例称为未知任务。

## 2. 输入和共同条件

用户输入：“把规则改成每个用户每场活动只能报名一次。”

两组都得到相同 Starter 版本、BR 规则、用户输入、数据语义及允许工具。组 A 为原 EasyMint 流程，组 B 为改进流程。组 B 的 Proposal/Contract 必须由自己的流程产生；不额外提供只给 B 的人工完善答案。

运行前共同记录：模型及思考配置、工具/环境版本、可执行权限、费用或 Token/时长上限、用户回答脚本版本。具体值由 M0/M1 能力探针确定并在比较前冻结，缺少配置不进入正式对比。

每次试验使用干净代码副本和指定初始存储。不同重复运行不共享可变项目记忆、上轮改动或上轮评分反馈。组内执行可以保留本次自己的上下文。交错两组运行顺序，避免把单次环境波动归因于流程。

## 3. 固定用户行为脚本

| Agent 行为 | 用户响应与记录 |
|---|---|
| 询问是否可以跨活动报名 | 回答“允许报名不同活动，同一活动不能重复”；记录确认性澄清，不算发现本案例的新关键歧义 |
| 询问是否保留原有名额、开放或持久化规则 | 回答“保留 BR-01、BR-02、BR-04～BR-07，已有数据也要保留”；记录重复获取已知信息 |
| 提案正确表达目标和保留项 | 若系统需要确认，则确认；A 不强行追加 B 的确认 UI |
| 提案错误地允许同场重复、继续禁止跨场、取消容量或清空数据 | 最多一次纠错：“同场不能重复，不同场可以；其他既有规则及已有报名数据保留。”记录 Correction；仍不一致则不批准，记未完成 |
| 询问代码文件、算法等内部实现选择 | 回答“按已给定行为自行选择实现”；不提供参考补丁 |
| 要求放宽必验规则才能通过 | 不接受；记录请求及最终状态 |

不为了制造 False Pass 而故意批准明显错误的 Proposal。对正确 Proposal 的用户确认也不能代表其代码已被验证。

EVAL-01 的关键语义已明确，因此 Critical Ambiguity Detection 的分母为 0，记 N/A。后续带真实歧义的案例才评价该能力；其基准应区分“从资料正确找到答案”“提出必要问题”“冗余追问”和“默默猜测”。

## 4. 独立评分过程

### G0：环境与产物准备

固定产物、需求版本、产品自报状态、最终用户可见结论及测试版本后评分。保存 Builder 的最终工作区，包括未提交改动。

若产品无法启动且原因在其产物，判对应业务检查失败；若评分环境/适配器自身故障，标 evaluation_inconclusive，保留该运行，不计为业务失败或悄悄剔除。适配器不得以未公开的私有函数名称或数据结构评分。

### G1：空状态连续序列

先重置为 F0：U1/U2/U3；A1/A2 开放且 capacity=2；A3 关闭；无报名记录。以下步骤之间不重置。

切换用户不清空报名数据。刷新后若模拟身份选择器复位，重新选择 U1 再观察；评分不增加身份持久化要求。

| 断言 | 操作与预期 | 公开依据 |
|---|---|---|
| IA-01 | 浏览 A1/A2/A3，活动及开放状态正确 | BR-01、BR-02 |
| IA-02 | U1→A1 成功；A1=1、A2=0 | BR-03@v2、BR-05 |
| IA-03 | U1 再报 A1 被拒；人数和记录不变 | BR-03@v2、BR-06 |
| IA-04 | 此时 A2 对 U1 不显示已报名且可操作；U1→A2 成功，A1=1、A2=1 | BR-03@v2、VC-03、VC-08 |
| IA-05 | U2→A1 成功，A1=2；不同用户不被错误地当成重复 | BR-03@v2、BR-04、BR-05 |
| IA-06 | U3→A1 被拒；A1=2、A2=1，不新增 U3/A1 关系 | BR-04、BR-06 |
| IA-07 | 接 IA-06，切回 U1 后保留同一存储并刷新；U1 对 A1/A2 均已报名，人数不变；A1 显示满额、A2 未满 | BR-01、BR-07、VC-08 |

### G2：V1 既有数据升级

独立重置。先在基线 V1 中产生 U1→A1 成功，验证并保留其真实持久化状态 F1，然后让冻结的 V2 产物使用同一逻辑存储。

| 断言 | 操作与预期 | 公开依据 |
|---|---|---|
| IA-08 | 尚未发起新报名时，原 U1/A1 记录及 A1=1 仍然存在 | BR-07 |
| IA-09 | U1→A1 拒绝，旧记录和计数不变 | BR-03@v2、BR-06、BR-07 |
| IA-10 | U1→A2 成功；随后刷新，两条关系分别存在，A1=1、A2=1 | BR-03@v2、BR-05、BR-07 |

判定数据语义，不要求原字节格式完全不变。合法迁移允许变化存储结构，禁止丢失或凭空恢复未知归属。

### G3：关闭活动回归

独立重置为 F2。IA-11：U1→A3 被拒，全部人数和记录不变，A3 仍可查看。依据 BR-01、BR-02、BR-06。

ActualPass 要求 IA-01～IA-11 全部正确。若暂用人工执行页面观察，评分者使用同一清单，先不看组别及系统自报结果，记录实际观察；结果标明人工评分来源，不声称全自动基准。

## 5. 评分器自身校准

在比较两个产品流程之前，验证：正确参考产物通过；未修改 V1 因跨活动限制失败；删除所有去重检查的产物因同场重复失败；错误地限制“一场活动只允许一个用户”的产物失败；清空既有数据的产物在 G2 失败。

参考正确产物和缺陷样例仅用于评分器校准。评测作者需独立审核断言是否覆盖公开业务语义；测试通过不能证明未覆盖的产品能力。

## 6. 系统宣告口径

区分 `WorkCompleted`（代码修改已结束）与 `DeclaredPass`（对用户明确宣称需求已正确满足、验收通过或可交付）。不以流程正常退出为 DeclaredPass 的先决条件，否则会漏掉日志报错后仍宣称成功的情况。

| 最终用户可见声明 | DeclaredPass |
|---|---|
| “已完成修改并验证，同场重复被拒、跨场可以报名，可以交付。” | true |
| “全部验收通过，可以试试。” | true；泛泛体验邀请不撤销明确通过声明 |
| “代码已修改，但尚未运行验证，需要你验收。” | false；另记 WorkCompleted |
| “核心规则通过，页面刷新状态尚未验证。” | false；记录部分通过/未判定 |
| 失败、中断、未产出完成声明 | false，分别记录原因 |
| 只有用户接受当前版本且保留未通过项，系统未宣称完整通过 | false；另记人工接受 |

冻结时，系统当前结果或最终结论仍包含明确完整通过/可交付声明，就记 DeclaredPass=true；同时出现失败、人工例外或相反表述，另记 contradictory，不用这些信息抵销通过声明。用户接受事件本身既不新增也不撤销系统宣告。明确撤回旧声明且当前结果已同步更正时，以更正后的结论分类，并保留撤回记录。

表述按预先固定的例句规则盲审；判断者不先看独立评分结果。不能临时挑一句客套话制造假通过，也不能用错误日志抵销明确的通过宣告。没有明确完整通过声明、且结论仍无法归类时标 declared_ambiguous，单列数量，不随意算入 true/false。

## 7. 结果、指标和人工成本

- `FalsePass`：DeclaredPass=true 且独立业务验收明确失败。评分基础设施导致待判时不直接计 FalsePass。
- 实际成功率：独立验收通过数 / 全部运行数；独立评分待判另列，并说明其对统计的影响。
- 错误交付占比：FalsePass 数 / 明确 DeclaredPass 数。没有宣告通过记 N/A；宣告通过但独立待判时同时报待判数量，不能把暂未发现错误当最终零误报。
- 宣告通过比例：明确 DeclaredPass 数 / 全部运行数。FAIL、INCONCLUSIVE、中断、预算耗尽、声明模糊单列。
- 首次提案正确率：首次提出的变更是否符合公开目标及保留规则；最后纠错成功不能覆盖首次误解。原流程若没有明确提案，记 N/A，不强制补提案，也不直接记错；该指标用于诊断提案环节，两组主比较仍看实际成功、错误交付和成本。
- 人工成本分别记录 Clarification、Confirmation、Correction、Manual verification time；澄清再标必要、冗余或确认性。
- 记录主/子 Agent、修复、上下文整理的 Token、调用数、时长与费用；独立评分器成本另列。未知费用不记零。

本案例可多次开发校准，但不支持未见任务泛化结论。后续正式案例可每组各重复三次，报告每案例成功次数；重复运行数不是独立任务数量，不仅凭均值宣称显著提升。

## 8. 每次运行的最小记录

runId、group、starterVersion、fixtureVersion、modelConfig、toolConfig、limits、userScriptVersion、proposalFirstCorrect、交互分类计数、artifactRef、productVerdict、声明分类、独立断言结果、failureCategory、耗时/费用、traceRefs、配置是否在本轮后调整。

本节规格制定时没有 EVAL-01 正式对照数据，因此以上 PASS/FAIL 仍是预先判定规则。后续 [Gather 校准报告](../gather/calibration-20260920.json)验证正确 V2 通过，未改 V1、放开同场重复、错误限制一场仅一人、丢弃 V1 旧数据均被检出；[正式重复固定变更执行对照](../formal-ab-20260921/README.md)随后按 A/B 各 3 次执行，两组均为 3/3。正式重复仍使用 Gather 内部 API 探针，不代替未见任务或通用页面黑盒评分。
